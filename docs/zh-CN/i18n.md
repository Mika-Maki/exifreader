# 国际化(i18n)策略

[English](../i18n.md) | **简体中文**

本仓库以多种语言提供文档。本页是其中的约定:译文放在哪里、什么必须翻译、什么绝不
翻译,以及规则如何被强制执行。

## 语言

| 标签 | 语言 | 状态 |
|------|------|------|
| `en` | English | **规范版本** —— 事实来源 |
| `zh-CN` | 简体中文 | 下表中所有页面均为完整译文 |

语言标签使用 [BCP 47](https://www.rfc-editor.org/info/bcp47)。新增语言时先选定标签
(例如 `ja`、`de`、`zh-TW`),然后按[新增一种语言](#新增一种语言)操作。

## 目录约定

```
README.md                     README.zh-CN.md
CONTRIBUTING.md               CONTRIBUTING.zh-CN.md
SECURITY.md                   SECURITY.zh-CN.md
AI_DISCLOSURE.md              AI_DISCLOSURE.zh-CN.md
docs/i18n.md                  docs/zh-CN/i18n.md
docs/en/usage.md              docs/zh-CN/usage.md
docs/en/architecture.md       docs/zh-CN/architecture.md
docs/en/formats.md            docs/zh-CN/formats.md
docs/en/faq.md                docs/zh-CN/faq.md
```

两条规则决定了这个结构:

* 仓库根目录下,`NAME.md`(英文)与 `NAME.<lang>.md`(译文)配对。这是 GitHub 的
  约定,便于发现翻译版首页。
* `docs/` 目录内,英文原文为 `docs/en/NAME.md`,译文为 `docs/<lang>/NAME.md`。

## 语言切换行

每个可翻译页面的**首行正文**都是语言切换行,当前语言加粗:

```markdown
[English](../i18n.md) | **简体中文**
```

链接相对于所在文件,因此 `docs/en/` 内的页面指向 `../zh-CN/usage.md`。
`scripts/check-i18n.sh` 会校验每一对文件的**双向**链接都存在且可达。

## 翻译什么,不翻译什么

会翻译:

* 下表列出的所有页面;
* Issue、Pull Request 与提交正文中面向人的说明(属约定,未强制校验);
* README 中对工具的说明。

**刻意不翻译**的内容:

| 内容 | 原因 |
|------|------|
| `CHANGELOG.md` | 它是与 git 标签、GitHub Release 说明对应的发布产物;翻译会形成两份会漂移的历史。发布要点的中文说明应放在中文 README 或 Issue 中。 |
| `CODE_OF_CONDUCT.md` | [贡献者公约](https://www.contributor-covenant.org/)提供官方译文,且其执行条文会被逐字引用。请链接官方译文,不要另起一份。 |
| `LICENSE` | 只有英文许可证文本具有法律效力。 |
| 标签名、IFD 名、枚举标签与厂商标识 | 它们必须与大家正在排查的规范、厂商文档一致。`ExposureTime`、`GPSLatitude`、`[normal]`、`Nikon type 3` 在任何语言下都保持原样。 |
| CLI 选项与机器可读输出 | `--max-depth`、JSON 键、`IFD0 | Name (0x1234) | value | TYPE[n]` 布局与退出码都是脚本解析的接口,翻译会破坏用户脚本。 |
| 代码注释与标识符 | 贡献者以同一种语言阅读代码;混语言的注释会增加评审难度。 |

由此得出的实际结论:**工具输出为英文**,中文 README 也明确写了这一点。若你需要本地化的
人类可读输出,请自行格式化 JSON —— 所有取值与偏移都已是稳定、语言无关的结构。

## 新增一种语言

1. 选定 BCP 47 标签,例如 `ja`。
2. 复制英文页面并翻译:
   * `README.md` -> `README.ja.md`
   * `CONTRIBUTING.md` -> `CONTRIBUTING.ja.md`
   * `SECURITY.md` -> `SECURITY.ja.md`
   * `AI_DISCLOSURE.md` -> `AI_DISCLOSURE.ja.md`
   * `docs/i18n.md` -> `docs/ja/i18n.md`
   * `docs/en/*.md` -> `docs/ja/*.md`
3. 在**每个**页面的语言切换行中加入该语言,包括已有的英文与中文页面。
4. 运行 `./scripts/check-i18n.sh`,然后提交 Pull Request。无需登记:脚本按文件名自动
   发现配对,因此"译文没有链接到原文(或反之)"在机制上就无法通过。

`docs/` 下允许只翻译一部分页面 —— 请在上表状态中列出尚未翻译的页面,不要留下静默落后的
页面。若要在语言切换行中宣传某种语言,根目录的 `README.<lang>.md` 应当先存在。

## 强制校验

```sh
./scripts/check-i18n.sh
```

脚本**不**依赖文件清单,而是按文件名自动发现译文,然后检查:

* 根目录每个 `.zh-CN.md` 都有对应的英文页面,且两者在前 6 行内互链;
* `docs/zh-CN/*.md` 都有对应文件(`docs/en/`,或两个顶层页面 `docs/README.md` 与
  `docs/i18n.md`),且互链;
* 译文不成孤儿 —— `docs/zh-CN/` 下没有英文来源的页面会直接失败;
* 完全没有译文的 Markdown 文档仍需把读者引向中文文档,因此没有页面是死路。

CI 中它作为 `docs and i18n` 任务运行。缺少译文、缺少跳转链接,或链接指向错误的文件,都会
让构建失败,而不是发布一个指向空页面的死链。

## 翻译质量

中文页面由撰写代码的同一套 AI 系统产出,并做过术语审校。术语被刻意保持一致:

| English | 简体中文 |
|---------|----------|
| container | 容器 |
| payload | 载荷 |
| information tree | 信息树 |
| offset (stored / file) | 偏移(存储 / 文件) |
| entry count | 条目数量 |
| bounds check | 边界检查 |
| hostile input | 恶意输入 |
| thumbnail | 缩略图 |

如果某处译文有误或不自然,那就是一个缺陷 —— 请直接对译文页面开 Issue 或 Pull Request。
修正译文无需改动英文原文。

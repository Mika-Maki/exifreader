# Internationalisation (i18n)

**English** | [简体中文](zh-CN/i18n.md)

This repository ships its documentation in more than one language. This page is
the contract: where translations live, what must be translated, what must not,
and how the rules are enforced.

## Languages

| Tag | Language | Status |
|-----|----------|--------|
| `en` | English | **Canonical** - the source of truth |
| `zh-CN` | 简体中文 (Simplified Chinese) | Complete for every page in the table below |

Language tags use [BCP 47](https://www.rfc-editor.org/info/bcp47). A new
language is added by picking a tag (for example `ja`, `de`, `zh-TW`) and
following [Adding a language](#adding-a-language).

## Layout

```
README.md                     README.zh-CN.md
CONTRIBUTING.md               CONTRIBUTING.zh-CN.md
SECURITY.md                   SECURITY.zh-CN.md
AI_DISCLOSURE.md              AI_DISCLOSURE.zh-CN.md
docs/i18n.md                  docs/zh-CN/i18n.md
docs/en/usage.md              docs/zh-CN/usage.md
docs/en/architecture.md       docs/zh-CN/architecture.md
docs/en/formats.md            docs/zh-CN/formats.md
docs/en/faq.md                docs/zh-CN/faq.md
```

Two rules produce that shape:

* At the repository root, a page named `NAME.md` (English) is paired with
  `NAME.<lang>.md` (translation). This is the GitHub convention that makes
  translated front pages discoverable.
* Inside `docs/`, the English original is `docs/en/NAME.md` and translations
  are `docs/<lang>/NAME.md`.

## The language switcher

The **first content line** of every translated or translatable page is a
switcher listing every language, with the current one in bold:

```markdown
**English** | [简体中文](README.zh-CN.md)
```

Links are relative to the file that contains them, so a page inside
`docs/en/` links to `../zh-CN/usage.md`. `scripts/check-i18n.sh` verifies
that both directions of every pairing exist and are reachable.

## What is translated, and what is not

Translated:

* every page listed in the table below,
* user-facing prose in issues, pull requests and commit bodies (by convention,
  not enforced),
* the description of the tool in the README.

**Not** translated, deliberately:

| Thing | Why |
|-------|-----|
| `CHANGELOG.md` | It is a release artifact that mirrors git tags and GitHub release notes; translating it would create two histories that drift. Translations of release highlights belong in the Chinese README or an issue. |
| `CODE_OF_CONDUCT.md` | The [Contributor Covenant](https://www.contributor-covenant.org/) publishes official translations and its enforcement text is quoted verbatim in reports. Link to the official translation instead of forking the text. |
| `LICENSE` | Only the English licence text is legally operative. |
| Tag names, IFD names, enum labels and vendor strings | They must match the specifications and vendor documentation people are debugging against. `ExposureTime`, `GPSLatitude`, `[normal]`, `Nikon type 3` stay as they are in every language. |
| CLI options and machine-readable output | `--max-depth`, the JSON keys, the `IFD0 | Name (0x1234) | value | TYPE[n]` layout and the exit codes are an interface that scripts parse. Translating them would break users. |
| Code comments and identifiers | Contributors read the code in one language; mixed-language comments make review harder. |

The practical consequence: **the tool's output is English**, and the Chinese
README says so explicitly. If you need localised human-readable output, format
the JSON yourself - every value and offset is already in a stable,
language-neutral shape.

## Adding a language

1. Choose a BCP 47 tag, for example `ja`.
2. Copy the English pages and translate them:
   * `README.md` -> `README.ja.md`
   * `CONTRIBUTING.md` -> `CONTRIBUTING.ja.md`
   * `SECURITY.md` -> `SECURITY.ja.md`
   * `AI_DISCLOSURE.md` -> `AI_DISCLOSURE.ja.md`
   * `docs/i18n.md` -> `docs/ja/i18n.md`
   * `docs/en/*.md` -> `docs/ja/*.md`
3. Add the language to the switcher line of **every** page, including the
   existing English and Chinese ones.
4. Run `./scripts/check-i18n.sh` and open the pull request. There is nothing to
   register: the script discovers pairs by filename, so a translated page that
   does not link to its source (or vice versa) is a failure by construction.

Adding a partially translated language is fine for `docs/` - list the pages you
have not translated in the status table above, rather than leaving a page that
silently lags. The root `README.<lang>.md` should exist before the language is
advertised in the switcher.

## Enforcement

```sh
./scripts/check-i18n.sh
```

The script does **not** take a list of files. It discovers translations by
filename and then checks:

* every `.zh-CN.md` at the root has an English base page, and both link to each
  other within the first 6 lines;
* every `docs/zh-CN/*.md` has a counterpart (`docs/en/`, or the two top-level
  pages `docs/README.md` and `docs/i18n.md`), and both link to each other;
* no translation is orphaned - a page under `docs/zh-CN/` without an English
  source fails;
* a Markdown document with no translation at all still links readers to the
  translated documentation, so no page is a dead end.

It runs in CI as the `docs and i18n` job. A missing translation, a missing jump
link or a link that points at the wrong file fails the build rather than
shipping a dead language link.

## Translation quality

The Chinese pages were produced by the same AI system that wrote the code, then
reviewed for terminology. Terminology is kept consistent on purpose:

| English | 简体中文 |
|---------|----------|
| container | 容器 |
| payload | 载荷 |
| information tree | 信息树 |
| offset (stored / file) | 偏移(存储 / 文件) |
| entry count | 条目数量 |
| bounds check | 边界检查 |
| hostile input | 恶意输入 |
| thumbnail | 缩略图 |

If a translation is wrong or awkward, that is a bug - please open an issue or a
pull request against the translated page. Corrections to a translation never
require touching the English original.
